COMPANY-WIDE OPERATIONAL ONTOLOGY · RESEARCH SNAPSHOT · 2026-09-09

公司级不要做“更大的 Obsidian”

目标不是把所有资料画成知识图谱，而是让多个业务系统能用同一套业务语义协作，并让人和 AI 都只能通过受控业务动作改变真实状态。

推荐底层逻辑：“联邦式业务对象层 + 受控动作层 + 工作流编排 + 权限/规则/审计”。各系统仍拥有各自事实；中央层负责统一理解、查询、决策与有证据的写回。
01 原始系统

事实仍归原系统

EAM、EHR、集控、ERP、钉钉、文档库。不要迁走后再造一套主数据。

02 集成与主数据

统一 ID、来源、时效

对象映射、数据质量、变更捕获。每项事实声明权威系统，避免“本体副本”变新孤岛。

03 业务对象层

对象、关系、可查询语义

人员、场站、设备、工单、风险、证据等跨系统对象；读模型可加速，不能偷换事实所有权。

04 受控动作与编排

动作、状态、恢复

全部写入经过命名动作、规则、幂等、Outbox、回读验收。工作流只协调，不直接越权改库。

05 人与 AI 应用

统一入口，权限同责

看板、移动端、Agent、Skill。AI 负责理解与建议，不能绕过动作门禁；每次读取也带身份。

系统事实 ──→ 统一对象与动作 ──→ 受控写回 + 独立回读

底座怎么选

能力建议起点为什么
事务/业务台账PostgreSQL + 对象关系表 + 事件/审计表权限、事务、报表和研发生态最稳。RLS 可做行级隔离，但表所有者和 BYPASSRLS 可绕过，必须单独设计运行账号。
统一业务定义Git 管的 Schema-as-Code；优先评估 LinkML定义可评审、差异可追踪。LinkML 能从一个模型生成 JSON Schema、OpenAPI、GraphQL、SQL、文档以及 RDF/SHACL 等，而不是 Markdown/YAML 双向维护。
流程与长事务Temporal（AI/系统重试、等待、恢复）活动拆成幂等小步骤，工作流持久化活动结果；适合外部系统慢、结果未知、要断点续跑的闭环。
审批/人机流程Flowable（需要 BPMN/DMN/CMMN 时）成熟的 Java BPM 平台，适合可视化审批、人任务、规则表；别拿它替代业务对象层。
细粒度授权OpenFGA；早期先用 Postgres RLS关系型授权适合“谁能看/办哪座站、哪个工单”；授权与业务规则是两回事，不能混用。
规则决策代码规则优先；跨系统政策再评估 OPAOPA 能将策略决策从应用中拆开；但 Rego 会增加另一门语言，刚起步不要把每条业务规则都塞进去。

不该作为主底座的东西

Obsidian

保留为制度、调研、业务解释、模型审查入口；不负责并发写入、权限、实时事实、事务或可靠恢复。

先上图数据库 / RDF / OWL

它们适合复杂关系分析、标准互操作和语义校验，不自动解决审批、写回、权限、队列和异常恢复。需要时再让 LinkML/SHACL 或图查询成为对象层的补充。

一上来照抄 Palantir

学的是模式：对象 + 链接 + 动作 + 动态权限 + 回写。不是复刻它的微服务数量和产品边界。

电力域要预留 CIM 映射

IEC 61970-301 CIM 定义公用事业对象、属性与关系，适合作为设备/电网/SCADA 语义互操作参照；不要硬把行政、人事、审批业务塞进 CIM。

公司级最重要的三条硬规则

  1. 一项事实一个权威系统。例如设备台账、人员组织、工单状态分别归明确来源；对象层只映射、索引和记录刷新时间。
  2. 一项业务决定一个命名动作。“批准整改”“指派负责人”是动作；不允许 Agent 或前端直接改状态字段。动作负责校验、审计、外部写回与拒绝原因。
  3. 读取、写入、AI 调用都带 actor。同样的规则管人和 Agent；AI 不应因拥有工具而跳过数据范围、审批权限和复核要求。

分阶段，不要空转一年

现在：Obsidian 设计台
保留现有知识库。每条业务输出对象、事实来源、动作、规则、状态、验收；稳定 ID 和来源字段从第一天就写。
一到两个真实闭环：模块化单体
PostgreSQL + API + 受控动作 + 审计/Outbox + 现有 EAM/钉钉适配器。先证明回读、恢复、幂等。
跨部门复用：中心定义仓
把验证过的共享对象定义转入 Git Schema；建映射和变更评审，不迁移所有业务数据。
规模化：分域联邦
按生产运维、安监、人资、经营等域设数据负责人；引入 Temporal/Flowable、OpenFGA、目录/血缘。图/SHACL 只在确有关系推理和互操作需求时加入。

调研到的公开参考

参考能学什么不能直接当什么
Palantir Foundry Ontology对象、链接、动作、动态权限、写回的整体模式。不是开源落地方案；也不需复制其微服务架构。
operational-ontology（MIT）极小参考：事实归源、写入走动作、规则拒绝、审计、回写。作者明确说它不是框架，且文档也提示认证、分布式写回与规模索引需自行补齐。
LinkML（Apache-2.0）把领域模型作为可生成、可校验、可版本化的定义。不是运行时本体库，也不提供工作流和权限。
SHACL / Apache Jena对 RDF 图做结构/约束校验；适合后期跨域语义校验。不是业务状态机或业务规则引擎。
Temporal（MIT） / Flowable（Apache-2.0）前者强在可靠长事务；后者强在 BPMN/人机流程。二选一看业务，不能承担共享语义与主数据。
OpenFGA（Apache-2.0） / OPA分别解决关系型授权与可审计政策判断。授权不等于业务规则，别混成一个万能规则层。

调研基于各产品官方文档、标准页和 GitHub 主仓库（2026-09-09）。Camunda 8 当前生产授权并非纯开源，未列为默认推荐；WebProtégé适合协作编辑 OWL，本身也不覆盖业务执行。GitHub 项目的活跃与许可证已做 API 核验，具体企业部署仍需安全、网络、数据分级和采购评估。
