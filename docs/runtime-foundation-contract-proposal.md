# 业务运行底座：发行、模块契约与业务装配

署名：Laiqh

状态：架构决策提案，非已实现能力。未安装组件，未修改业务包、生产配置或真实业务数据。文件中的模块名和接口名称是建议契约，不是已存在的命令/API。正式开发前须定位真实调度项目，按 mp-dev-flow、ai-project-preflight 核验并复用已有代码。

## 1. 产品边界

建设一个独立于 Agent 的业务运行产品。Agent 经受控接口提交意图与必要事实；运行程序负责可靠执行。Skill 是方法和使用说明，不是调度引擎；Hermes 插件不是产品承载边界；MCP 是宿主接入方式之一。

初期采用模块化单体：统一版本化发行，调度控制面和业务 Worker 分进程，数据库为持久状态源。不同业务共享运行核心，不复制队列、锁、恢复或看板。模块化不要求各模块独立部署为微服务。

## 2. 两种明确区分的部署方式

### A. 独立本机运行

首个拟支持目标：Windows x64（具体受支持系统版本在测试后发布）。交付自包含目录/安装包：私有 Python 运行环境、锁定依赖、编译后的本地 UI 资源、运行核心、受信业务包、版本清单、启动/诊断/备份入口。不依赖接收人的全局 Python、Node 或开发目录；不把开发者 venv 直接复制成发行包。

本机运行账本可用 SQLite WAL，限定本机磁盘和受控单写入路径，禁止多个机器用共享盘同时打开。此模式不承诺多机高可用。Worker 通过运行服务提交状态，不直接写数据库。

启动 BAT 前台可见，退出时清理本产品所属子进程。程序关闭则停止办事，数据保留；恢复前对未确定的外部结果进行回查。默认仅本机监听；远程开放须另行部署认证、授权、TLS、防火墙和审计。

### B. 连接已有运行中心

另一台电脑只配置 Agent 接口/打开控制台，任务仍由同一个服务端处理；不复制调度台账，不建立第二个相同的消息消费者。服务器多 Worker 模式拟采用 PostgreSQL 等经过验证的共享事务存储；需要单独验证任务领取、租约、防陈旧写入、迁移和灾备，不把 SQLite 更换连接地址说成无缝扩容。

部署到新公司与迁移原实例不同：前者仅复制获准定义/代码并重新绑定系统，后者才按授权迁移实例状态和证据。迁移原实例必须先暂停入口、处理在途结果、备份、迁移、对账并确认唯一有效消费者，旧实例停止后才启用新实例。独立数据库中的本机锁不能防止两台机器重复消费；跨实例主权需共享协调设施或明确且验证的停旧启新流程。导入/克隆默认不激活消费。

## 3. 环境验收与业务准入

安装成功、程序健康、业务可用、生产启用分别记录，不用一个绿色灯混为一谈。

启动诊断读取每个业务包声明的能力需求，逐项检查受支持 OS/架构、包和依赖完整性、数据目录权限/空间、端口、数据库 schema 版本、接头兼容性、合法认证、系统网络可达性、AI 节点所需模型能力和消费唯一性。

缺失业务能力时，展示准确阻断项并禁止该业务接单，不拖垮无依赖的其他业务。认证与真实业务绑定由获准输入提供，不从相邻缓存猜取。

浏览器自动化仅是特定接头依赖，不是核心必需。如需自带大型浏览器，单独能力包交付，下载前说明体积与原因。在线系统、远程模型、登录权限是外部前提，自包含安装包不等于业务完全离线。

安装诊断默认只读。外部写入能力的验收需要获准沙箱、独立回读及清理记录，不能通过在生产随意建测试单验证。

## 4. 模块用什么承载

| 模块 | 交付载体 | 边界 |
|---|---|---|
| 开发规范 | 蓝图 Skill、规范文档、模板 | 指导建模和责任分工，不作为唯一门禁 |
| 业务 SDK 与准入检查 | 版本化代码包、schema、验证器、测试套件 | 校验包结构、依赖、权限声明和行为；语义合理性仍需评审 |
| 运行核心 | 可安装代码发行包 | Case、节点、调度、持久化、幂等、等待、恢复、审计 |
| 模型服务 | 机器定义包与查询/校验代码 | 稳定身份、类型、关系、来源、规则绑定和版本 |
| 业务插件包 | 清单、流程声明、处理代码、AI模板、测试、SKILL.md | 只表达业务差异，不能注册任意调度核心修改 |
| 系统接头 | 受信 Adapter 代码包 | EAM/钉钉等读取、动作、回读；隔离凭据与会话 |
| 宿主接头 | MCP/HTTP/受控CLI适配层 | Hermes或其他Agent接入，不承载唯一任务状态 |
| 运行控制台 | 本地打包静态资源与只读查询API | 从台账与事件投影展示；失效不使调度丢失状态 |

业务插件属于本产品，不等于 Hermes 桌面插件。后者即使用于嵌入入口，也仅是可替换的 UI 外壳。

## 5. Skill规范必须变成开发产品

以现有 ai-closed-loop-platforms 和 ai-project-preflight 为方法权威，配套 SDK、模板、检查器、契约测试，不另建竞争的同类规范。

每个节点必须声明执行类别（确定性代码、受限AI、人工决定或受控外部动作）、输入输出schema、来源、前置依赖、允许能力、输出证据、错误类别和恢复策略。人工等待持久化并释放Worker；外部动作声明幂等、回读、结果未知时的对账方式；AI声明采用原因、结构化输出、证据、预算和不确定出口。

普通业务包不能任意开放终端或浏览器写入权限。能力声明仅是输入，实际权限必须由运行时/进程和凭据边界落实；不能声称独立Python进程本身就是安全沙箱。首版仅装受信、审查过的代码包；不开放任意第三方包安装。需要不受信代码时另建操作系统级隔离。

包摘要校验用于完整性；签名只有配合可信签发者和审核策略才有意义。检查器能证明字段/依赖/契约齐全，不能证明所有业务规则正确，需独立判据和业务审核。

## 6. 本体的最小运行架构

### 定义层

一个受版本管理的机器定义权威源，起步推荐受schema约束的YAML/JSON：稳定ID、命名空间、对象类型、关系类型、属性、权威来源声明、角色范围、规则/动作引用、有效期、发布状态、兼容性与迁移说明。

公共核心只共享确实同义的身份与定义。业务扩展通过明确依赖引用人、场站等对象，不复制它们；角色关联到具体业务和有效时间，资格与授权不因身份共享自动通用。

生成接口schema、文档和检索索引，不手工维护多份竞争权威。LinkML可以作为后续建模/生成工具验证，不成为首版强制依赖。Obsidian保留制度依据、解释和评审材料，正式机器规则的来源链接回证据；页面文字不会自动变成已发布规则。

### 实例与事实层

存储内部对象ID、外部标识映射、关系实例、事实来源、观测/有效时间、历史与证据引用。运行系统业务Case状态与外部业务对象状态分别保存；不把旧的观测当作当前真实状态。同名不直接合并；引用不仅检查字符串格式，还验证存在、类型、范围与授权。

初期关系表可用关系数据库实现，不因名为图谱就强制图数据库。只缓存有权限且确需的数据，不重造权威主数据系统。

### 受控调用层

建议接口职责：解析对象身份；按业务/权限查询对象及关系；读取当前节点绑定的定义；对动作评估适用规则；通过专用接头完成动作并回读。命名尚未实施。

运行时根据业务包与Case绑定取得精确依赖，不让Agent自由搜索并挑选权威规则。结构化规则或注册的受信规则函数负责确定性校验，不执行配置内任意脚本。AI只能提供候选，不能提交自行生成的“允许”结果替代服务端门禁。

动作写入前验证身份、授权及事实时效，处理检查到执行之间的变化。规则版本可追溯，但紧急撤销/生效规则不能被旧Case固定版本绕过；受影响Case暂停并重新评估，不静默升级或无限沿用旧规。

## 7. 一个新业务包怎样装配

1. 建模：引用已有对象，生成复用/新增/变更差异；角色、责任、事实来源和完成证据先明确。
2. 分工：用代码/AI/人工与受控动作分类每个节点，选择现有接头和处理器。
3. 打包：包清单列出ID、版本、所需运行核心/SDK/模型/接头/模型能力、权限范围、资源和迁移。
4. 静态验收：校验schema、对象引用、流程可达性、等待出口、依赖兼容性、禁止能力、证据要求。不要把每个业务强制写成无环顺序流程；允许显式有界循环和持久等待，禁止无边界自由规划。
5. 隔离验收：正常、拒绝、缺事实、重复、故障恢复、跨单污染、旧包回归和模型/接头不兼容。真实副作用只在获准沙箱验收。
6. 暂存安装：验证来源/完整性，解析锁定依赖；禁止导入时偷偷运行安装脚本或升级共享环境。新增依赖通过受验证环境发行/能力包提供；冲突依赖隔离到Worker环境。
7. 本地绑定：由授权人绑定系统、身份、凭据引用和数据范围，进行只读就绪检查。
8. 发布启用：明确批准后原子激活注册表；未激活包不能消费事件，路由冲突直接拒绝，不让Agent临场二选一。
9. 运行：入口解析业务类型，建独立Case，锁定兼容包版本、路由与证据；新业务自然出现在同一控制台。
10. 升级卸载：新Case使用新版本；旧Case默认按受支持版本继续或走显式迁移。规则撤销另有门禁；存在活跃Case或共享依赖时拒绝直接删除。数据库迁移先备份并验证回退边界；代码回滚不等于外部业务写回撤销。

正常新业务不改调度核心；确需新增执行原语时升级SDK/核心并回归所有适用包，不承诺任何业务都零代码扩展。

## 8. 发行物逻辑布局（建议，不是现存目录）

- app/：只读核心程序、私有运行环境、UI和诊断入口。
- packages/：已验收业务/模型/接头包，按版本管理。
- instance/：部署绑定、凭据引用、可用能力与激活状态。
- data/：受保护的任务账本、事件、事实缓存、证据与审计。
- backups/：受控备份与迁移清单。
- docs/：安装说明、支持矩阵、兼容清单、限制与发行验收报告。

程序升级不覆盖instance/data；凭据通过本机或服务器凭据存储注入，不打进业务ZIP。运行日志脱敏，证据权限和保留期限独立控制。

## 9. 看板数据契约

从Case/NodeRun/Event/Resource/Evidence及包注册信息读取。业务状态、Worker存活、外部接口可达性、数据新鲜度独立显示。没有新心跳应显示失联/未知，不能沿用绿色运行；断线重连按事件游标补读并与权威快照对齐。

显示业务包/规则版本、节点负责者、等待原因、重试/对账状态、资源占用、外部回读证据和更新时间。只读数据范围由后端授权过滤，不依赖前端隐藏。

初期只读；将来的暂停/重试/人工批准必须走独立受控动作入口，有状态前提、权限和审计，不能直接改数据库状态。

## 10. 交付验收门槛

- 在没有开发环境的受支持干净机器上，从最终发行包安装并启动；不能以作者电脑已安装依赖代偿。
- 中文/空格路径、非管理员权限、端口占用、目录不可写、缺网、认证失效、代理差异、磁盘不足均有明确失败出口。
- 包与运行核心版本不兼容时在启用前拒绝；未绑定接头的业务保持禁用。
- 进程终止并重启后任务恢复；外部写入结果未知时先对账，不承诺跨系统exactly-once。
- 导出导入后身份/关系/证据关联保持，获准迁移的历史完整，重复消费者不能同时启用。
- 第三项业务引用现有对象并注册，在无需修改调度核心的验证范围内跑通，旧业务回归通过。
- 不同业务受控并行，等待人不占执行资源，共享资源冲突正确互斥。
- 代码/AI/人工权限分工和独立回读由运行时验证；提示词拒绝越权不单独算通过。
- 看板断开不停止调度；台账不可用时写入失败关闭；看板不以旧缓存冒充实时。
- 发布报告逐项区分：已验证、未验证、不支持、外部前提。不得承诺在所有电脑和外部系统变化下零故障。

## 11. 实施顺序

本节更新为整体装配优先的候选顺序：先确认模块连接、固定语义和可变接头；补最小接口与共同冻结；经批准做两业务复用、双输入/输出替换的隔离装配样例；再逐层完善运行核心、共享模型、业务SDK与独立装配模块，最后做授权真实接入、发行和控制台验收。不以先做安装包替代业务装配验证。

详细模块归属、生命周期、失败出口及最小样例见 [整体装配修订候选](architecture-track/assembly-architecture.md)，总体任务及认领见根PROJECT_CONTROL.md。此修订仍待用户确认，不是批准扩大实现；现有spike保留为局部证据。
