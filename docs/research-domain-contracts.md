# 可增长复用业务图：LinkML 的实际位置

## 修正后的判断

目标不是全公司一次性统一建模，也不是选一套大型平台，而是：**车辆业务先建立 Person／Vehicle／Station，后续两票业务复用已有 Person／Station，逐步长成可移植、可映射真实运行状态的业务图。**

在这个目标下，**LinkML 值得作为“模块化模型定义与发布层”优先做小范围验证**；此前仅因现有代码偏 Python 而降低其优先级，忽略了跨业务模型复用这个关键收益。但它不是运行中的关系图，也不能单独完成数字孪生。官方把 LinkML 定位为 schema language，而不是 OWL 式本体推理语言。[2]

## 真正应先稳定的设计

- **同一对象，稳定身份。** Person、Vehicle、Station 的内部 ID 不随业务变化；EAM 编号、钉钉用户标识等作为有来源的外部标识映射，不能用姓名或显示名称认定是同一对象。
- **身份共享，角色属于场景。** 同一个 Person 可在出车单中是驾驶员，在工作票中是工作负责人。角色放在“人—具体业务单据”的关系上，保留适用时间；不要在 Person 上堆全公司所有角色字段，也不要为每种角色复制一份人员对象。
- **领域逐步增加，而非不断膨胀核心。** 最小核心只放身份、基本定义及必要共享关系；车辆模块增加出车单、用车关系，两票模块增加工作票、许可和职责关系。不同业务状态留在各自模块。DDD 的共享交换语言与上下文翻译原则支持这种边界，而非要求所有业务使用完全相同的内部模型。[1]
- **模型之外还要有可迁移实例。** 迁移包不仅有 schema，还应有对象、关系、外部标识映射及版本说明。数字孪生进一步需要状态／观测的时间、来源、质量和历史；“能画出关系图”不等于“已同步真实状态”。

以上是针对本场景的设计建议，不是任何工具自动提供的能力。

## LinkML 带来的价值与必须补上的缺口

价值在于把共享概念变成可管理、可发布、可供多个业务引用的定义，再派生文档和机器契约，而不是让每个 Skill 各自复制一套 Person。**若它确实减少重复定义和变更协调，采用理由就成立，不必等待公司规模变大。**

但必须守住一条边界：**共享 schema 不自动实现共享身份和关系完整性。** LinkML 的 JSON Schema 生成器会把非内嵌对象引用降为字符串，枚举附加元数据会丢失，额外／复合唯一键也不能完整映射。[3] 因此，一个 `person_id` 通过类型校验，不证明它指向真实、正确且有权执行该操作的人。身份解析、引用校验和权限仍须在运行层实现。

治理保持轻量：共享对象指定负责人；新业务优先复用，确有不同含义才扩展；核心变更须检查消费者兼容性；生成器版本固定并用真实案例验证。LinkML 官方也提醒各生成器维护与测试质量并不一致，应逐个目标评估，不能以“能生成”代替“生成后语义完整”。[4]

## 最有判断力的验证，不是工具对比

只验证一条增长路径：**车辆模块建立人员与场站 → 两票模块直接引用原有 ID → 同一人承担不同业务角色 → 两个模块共同导出、重载后身份和关系不变 → 新增两票字段不破坏车辆业务。** 同时测试无效引用、角色越权与版本不兼容能否被阻止。

如果 LinkML 让这条路径更少重复、更容易迁移，就采用；如果相同效果用现有 Python 契约加明确模块约定更简单，就暂不增加它。**优先建设的是可复用、可演化的对象关系契约；LinkML 是它的有力候选载体，不是目标本身。**
